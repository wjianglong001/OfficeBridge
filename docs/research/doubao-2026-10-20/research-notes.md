# 证据笔记

状态：调研完成；对路线存在性置信度较高，对本机完整兼容性未作结论。

## 事实

- 豆包工作具有自定义连接器；在豆包已有登录状态下也有工作入口，具体开放范围取决于客户端。[1]
- 草料给出 HTTP 连接器的完整接入过程；MediaClaw 给出本地 STDIO 连接器与插件配对过程。[2][9]
- Windows Gateway 作者明确报告单机 2.31.4 的有限实测，并将豆包内部 MCP、其他版本列为未验证项。[3]
- Gateway 的 server.mjs 接收明确 conversationId/runId，分别包装 create/send/wait/read，而非把所有对话历史交给调用方重放。[4]
- 安装脚本锁定上游 b790ea2d127922902f7dc461b4169c28a2438f26；Windows 补丁主要适配路径和进程生命周期。[5][6]
- 上游桌面支持说明针对 macOS；其文档列出会话停止和 MCP 调用参数。不能把上游全部能力自动归给 Windows 补丁。[7]
- 公开的豆包开放平台首页介绍 Skill/Plugin/OpenAPI，并注明内测；本轮未发现足以证明可直接控制个人已登录桌面会话的公开协议。[8]
- Patsnap 只报告 macOS 工具发现和任务选择；没有执行实际业务查询，支持证据必须限于它明确验证的范围。[10]
- 上游 protocol.mjs 在客户端渲染环境中提交远端聊天请求，使用内部协议路径；这不是公共 SDK，也不是完全离线处理。[11]

## 分析

完整体验有两条通道：侧栏提交任务、复用豆包会话、获取结果；豆包回调 OfficeBridge 表格工具。连接器只解决后一条，不能独自实现 WPS 内聊天。

Windows 项目证明已有具体适配尝试，不支持“豆包完全不能接入”的结论；但单机有限实测不能支持“本机现在完整可用”的结论。

本项目的 MCP 仅在 Agent 的当前 run 内授权。直接将其地址填进豆包，既有端口/令牌生命周期问题，也缺少任务绑定与侧栏捕获新快照的机制，需要新增适配逻辑。

## 核心结论的支撑摘述

- Windows 可用路线存在：[3] 的 Requirements/Limits 明确指定 Windows 10/11、已登录客户端、2.31.4 单机实测；[6] 存在实际 win32 分支。
- 连续会话有可参考的调用方式：[4] 的 continue_task 接收 conversationId，wait 接收 conversationId 与 runId。
- 内部表格工具链仍是缺口：[3] 明确不声称豆包内部 MCP 实测通过；本地 table-mcp.ts 对无活动任务拒绝 tools/call。
- 连接器路线具备实际产品参考：[2] 给出 HTTP 配置，[9] 给出 STDIO、本地插件配对与操作过程；两者均不是 OfficeBridge 实测。

## 缺口与冲突

1. 本机安装包 2.32.6 与 Windows Gateway 声明的 2.31.4 不同，协议兼容性未知。
2. 草料描述可通过对话安装，MediaClaw 要求人工保存连接器；应按不同工具/客户端实际能力处理，不能归纳为一律自动安装。
3. 上次调试启动在命令执行前被自动审批拒绝。该事件只证明当前工具执行受限，没有提供“豆包拒绝调试参数”的产品证据。本轮没有重试。
4. 权限模式 AskOnRisk 不等于严格只读或仅暴露表格工具，必须单独验证内置命令/文件工具的限制能力。[3][7]
5. 发布前还缺真实 Windows 连续会话、取消、工具调用与 WPS 回读的闭环验收；本轮没有模型请求。
